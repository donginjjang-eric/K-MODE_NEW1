# K-MODU 패션·뷰티 다중 작업공간 설계

## 목적

한 Google 계정이 크리에이터, 패션 브랜드, 뷰티 브랜드 중 필요한 작업공간을 독립적으로 사용할 수 있게 한다. 패션과 뷰티의 상품·캠페인·콘텐츠·거래·정산 데이터는 서로 섞이지 않아야 하며, 관리자는 각 계정의 작업공간 권한을 한곳에서 관리할 수 있어야 한다.

## 현재 문제

- `users.role` 한 값이 로그인 이후 이용 가능한 화면 전체를 결정한다.
- 크리에이터 프로필이 연결된 계정은 브랜드 파트너 신청이 차단된다.
- `getDesignerForUser`가 사용자에게 연결된 첫 브랜드 한 건만 반환한다.
- 패션과 뷰티 센터가 같은 `designers` 레코드를 기준으로 라우팅되어, 한 계정이 두 종류의 브랜드를 운영할 수 없다.
- 마스터 관리자도 연결된 패션 브랜드 때문에 뷰티 센터로 진입하지 못한다.

## 채택 구조

### 1. 계정과 작업공간 분리

`users.role`은 기존 호환성과 기본 로그인 목적지를 위해 유지하되, 실제 화면 접근 권한은 새 `user_workspace_memberships` 테이블로 판정한다.

작업공간 종류:

- `creator`: 개별 크리에이터 센터
- `fashion_partner`: 패션 브랜드 센터
- `beauty_partner`: 뷰티 브랜드 센터
- `admin`: 관리자 콘솔
- `agency`: 대행사 조회 센터

각 멤버십은 사용자와 실제 리소스를 연결한다.

- 크리에이터 작업공간 → `creator_accounts.id`
- 패션·뷰티 브랜드 작업공간 → `designers.id`
- 관리자 작업공간 → 리소스 없음
- 대행사 작업공간 → 관리 그룹 또는 대행사 범위

한 사용자가 같은 종류의 브랜드를 여러 개 운영할 가능성을 고려해 `(user_id, workspace_type, resource_id)`를 고유 키로 사용한다.

### 2. 브랜드 데이터 분리

브랜드의 상품·캠페인·콘텐츠·거래·정산은 기존처럼 `designer_id`를 소유 키로 사용한다. 패션과 뷰티는 브랜드 레코드의 `brand_category`로 구분하되, 접근 시 경로에 맞는 카테고리를 서버에서 다시 검증한다.

- 패션 경로: `K-패션`
- 뷰티 경로: `K-뷰티`
- 복합 브랜드: 두 센터 멤버십을 명시적으로 부여할 때만 양쪽 접근 허용

경로의 카테고리와 브랜드가 일치하지 않으면 다른 센터로 자동 이동시키지 않고, 사용 가능한 작업공간 선택 화면으로 보낸다. 이로써 잘못된 브랜드 데이터로 작업하는 것을 방지한다.

### 3. 인증과 화면 전환

로그인 후 사용 가능한 작업공간을 조회한다.

- 한 개면 해당 센터로 바로 이동
- 여러 개면 기본 작업공간으로 이동하고 상단 전환 메뉴에서 변경
- 요청한 경로가 권한 목록에 있으면 그 경로를 우선
- 권한이 없으면 작업공간 선택 화면과 신청 안내를 표시

현재 선택한 브랜드는 URL의 작업공간 ID로 식별한다. 단순 클라이언트 쿼리만 믿지 않고 모든 페이지와 API에서 로그인 사용자의 멤버십과 리소스 소유권을 재검증한다.

### 4. 관리자 콘솔

`회원·승인 관리`의 계정 상세 또는 우측 패널에 작업공간 관리 영역을 추가한다.

- 보유 작업공간 목록
- 크리에이터·패션·뷰티 신청 상태
- 작업공간 승인·비활성화
- 기존 브랜드 연결
- 새 브랜드 신청 생성
- 기본 작업공간 지정

관리자 상단 전환 메뉴는 관리자 콘솔, 크리에이터 화면, 패션 브랜드 센터, 뷰티 브랜드 센터를 각각 표시한다. 마스터 관리자는 전용 패션·뷰티 미리보기 브랜드를 사용하므로 한쪽 카테고리에 종속되지 않는다.

### 5. 신청 흐름

크리에이터 계정도 브랜드 파트너 신청을 할 수 있게 기존 역할 충돌 차단을 제거한다. 신청 시 분야를 `K-패션`, `K-뷰티`, `복합` 중 선택하고, 브랜드 레코드와 대기 멤버십을 함께 만든다.

승인 시 해당 작업공간 멤버십을 활성화한다. 반려·비활성화 시 다른 작업공간은 그대로 유지한다.

### 6. 기존 데이터 이관

배포 시 멱등 마이그레이션으로 기존 연결을 멤버십으로 자동 이관한다.

- `users.role = admin` → `admin`
- `creator_accounts.user_id` → `creator`
- `designers.user_id` + 패션 분야 → `fashion_partner`
- `designers.user_id` + 뷰티 분야 → `beauty_partner`
- 복합 분야 → 패션·뷰티 두 멤버십
- 대행사 사용자 → `agency`

기존 `user_id`, `users.role`, 상품과 캠페인 외래키는 제거하지 않는다. 첫 배포는 이중 판정으로 호환성을 유지하고, 새 멤버십이 없을 때만 기존 역할로 제한적으로 보완한다.

### 7. 오류 처리와 감사

- 권한 없음: 403 또는 작업공간 선택 안내
- 승인 대기: 해당 작업공간만 잠금, 다른 센터 사용 가능
- 잘못된 브랜드 종류: 데이터 노출 없이 선택 화면으로 이동
- 작업공간 변경·승인·비활성화는 감사 로그에 사용자, 관리자, 리소스, 이전/이후 상태를 기록
- 일부 마이그레이션 실패 시 전체 트랜잭션을 롤백하고 앱 시작을 중단해 불완전한 권한 상태를 허용하지 않음

## UI 구성

### 상단 전환

- 관리자 콘솔
- 크리에이터 화면
- 패션 브랜드 센터
- 뷰티 브랜드 센터

사용 권한이 있는 항목만 일반 계정에 표시한다. 마스터 관리자는 네 항목을 모두 본다.

### 작업공간 선택 화면

브랜드명, 분야, 승인 상태, 최근 활동을 카드로 표시한다. 신청 중인 작업공간도 보이되 진입 버튼 대신 상태와 다음 조치를 안내한다.

### 모바일

상단 전환은 가로 스크롤 탭으로 유지하고, 브랜드가 여러 개인 경우 먼저 브랜드 선택 바텀시트를 연다. 핵심 업무 메뉴는 각 센터의 기존 모바일 내비게이션을 유지한다.

## 테스트 전략

- 마이그레이션 멱등성과 기존 계정 자동 이관
- 한 계정의 크리에이터+뷰티 동시 접근
- 한 계정의 패션+뷰티 브랜드 데이터 격리
- 승인 대기 작업공간만 차단되는지 확인
- API가 다른 브랜드 `designer_id` 접근을 거부하는지 확인
- 관리자 네 작업공간 전환과 일반 사용자의 허용된 탭만 표시
- 기존 디자이너 스튜디오·크리에이터 센터 회귀 테스트
- PC와 모바일에서 전환·선택·상품 등록 흐름 브라우저 검증

## 완료 기준

- `studioooat@gmail.com` 같은 기존 크리에이터 계정에 뷰티 브랜드 작업공간을 추가할 수 있다.
- 패션 브랜드와 뷰티 브랜드 상품이 각 센터에서만 표시된다.
- 같은 계정이 각 센터를 전환해도 기존 크리에이터 데이터가 유지된다.
- 관리자가 계정별 권한과 승인 상태를 한 화면에서 관리한다.
- 기존 패션 디자이너 스튜디오 기능과 운영 데이터가 손상되지 않는다.
